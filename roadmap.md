# Chopsticks Roadmap

Chopsticks prepares and runs CBT against MicroCeph clusters. The plan progresses through ordered phases, each documenting prerequisites, deliverables, rollback, and known limitations to keep development auditable.

## Phase 0 – Pre-Flight Checks
- **Prerequisites:** Operator supplies reachable MicroCeph endpoints, authentication details, and baseline hardware/resource expectations.
- **Objectives:** Implement a pre-flight CLI that validates cluster health (`microceph status`, optional `ceph status`), network reachability between controller and nodes, disk capacity, and host resource baselines prior to any automation.
- **Deliverables:** `chopsticks preflight` command emitting structured reports, baseline requirement documentation, and issue triage guidelines.
- **Tests:** Unit tests for each probe collector; integration test against a controlled MicroCeph environment; regression suite ensuring probe additions remain backward compatible.
- **Documentation:** Operator pre-flight checklist describing expected outputs and remediation steps when checks fail.
- **Validation:** Execute the pre-flight command on a staging cluster and capture the signed report prior to advancing to Phase 1.
- **Rollback:** None required; pre-flight is read-only. Disable probes via configuration if regressions are discovered.
- **Known limitations:** Requires an already-bootstrapped MicroCeph cluster; does not remediate failures automatically; MicroCeph bootstrap and node join operations remain operator-owned and outside Chopsticks scope.

## Phase 1 – Foundation & Packaging Baseline
- **Prerequisites:** Phase 0 report shows no blocking issues; developer workstations meet tooling requirements (snapcraft, uv, LXD/multipass); shared understanding that the Chopsticks controller will act as the CBT head node with direct SSH reachability to all cluster members.
- **Objectives:** Establish Python project structure (`pyproject.toml`, lint/test scaffolding); define classic confinement snapcraft layout with separate parts for Chopsticks core and CBT; enforce dual `uv` environments (core vs CBT); select and document a pinned CBT tag/commit for the compatibility matrix; capture high-level architecture showing controller=head node and SSH topology; and lay the groundwork for uniform error handling and security expectations.
- **Deliverables:** `snapcraft.yaml` with `chopsticks-core` and `cbt-vendor` parts; corresponding `uv.lock` files; architecture diagram plus narrative establishing controller/head co-location; compatibility matrix seed (YAML describing Chopsticks, CBT, MicroCeph, Ubuntu combinations); CI workflows (lint, unit, `uv lock`/`uv sync`, snapcraft build); error-code namespace and structured logging specification; threat model covering SSH/key handling, configuration ingestion, and subprocess execution; and phase template (prereqs/deliverables/rollback/limitations) for future updates.
- **Tests:** Unit tests for CLI bootstrap; static analysis (ruff, mypy); CI checks ensuring both `uv` lockfiles are deterministic; snapcraft lint; smoke test confirming the dev snap exposes CLI stubs and bundled CBT entry scripts; automated check verifying compatibility matrix schema validity and architecture documentation presence.
- **Documentation:** Developer setup guide covering `uv` workflows, snapcraft parts, CBT version pinning policy (criteria, review cadence, override stance), architecture/SSH topology expectations, classic confinement justification (including mitigations and future strict evaluation), error-handling standards, threat model summary, and compatibility matrix maintenance process (update triggers, publication path, runtime warnings for untested combos).
- **Validation:** Build and install the developer snap (`snapcraft pack`, `snap install --dangerous`); verify both `uv` environments activate via snap hooks; confirm CBT binaries from the vendored part are addressable; run CI pipelines to ensure compatibility matrix and error-handling specs pass validation; record outputs in the validation log.
- **Rollback:** Revert to the baseline repository snapshot prior to introducing snapcraft parts; drop generated lockfiles if incompatibilities surface; remove compatibility matrix entries and architecture docs if design direction changes.
- **Known limitations:** Classic confinement required for remote orchestration; strict confinement evaluation deferred to Phase 9. Initial compatibility matrix coverage is limited to baseline MicroCeph/Ubuntu combinations until Phase 6 expands automated validation.

## Phase 2 – SSH Credential Import
- **Prerequisites:** Foundation snap builds successfully; operators provide SSH keypairs and target node inventory.
- **Objectives:** Implement commands to ingest operator-supplied private/public keys, enforce permissions, distribute keys across nodes, and validate passwordless SSH plus sudo (`sudo -n true`).
- **Deliverables:** `chopsticks ssh import` command suite, secure storage of staged credentials, remediation guidance surfaced on validation failures, and automated cleanup command to revoke keys.
- **Tests:** Unit tests for permission handling and filesystem hygiene; integration tests using containerized hosts to verify SSH connectivity and passwordless sudo; snap interface tests ensuring classic confinement grants required filesystem and SSH client access; rollback tests confirming `chopsticks ssh remove` succeeds and is idempotent.
- **Documentation:** Operator instructions detailing key formats, command usage, error diagnostics, and `/etc/sudoers.d/` configuration patterns to satisfy CBT requirements.
- **Validation:** Use the packaged snap to import keys on a staging cluster, confirm `ssh` and `sudo -n true` succeed for each host, and archive the validation log.
- **Rollback:** Provide `chopsticks ssh remove` to delete staged keys and revert permissions if problems occur.
- **Known limitations:** Tool validates sudo configuration but does not edit sudoers files; operators must remediate configuration gaps manually.

## Phase 3 – Topology Discovery & OSD Strategy
- **Prerequisites:** Successful SSH/sudo validation from Phase 2 and accessible MicroCeph nodes.
- **Objectives:** Discover MicroCeph topology via operator manifests and remote queries, detect MicroCeph-managed OSDs versus unmanaged devices, and automatically select safe CBT modes (`use_existing: true`) when MicroCeph controls storage.
- **Deliverables:** Inventory module capturing node roles, services, device ownership, and network mappings; disk-strategy decision record documenting when CBT provisioning is disabled; warnings surfaced when unsafe combinations are detected.
- **Tests:** Unit tests exercising topology parsers with curated fixtures; integration tests against staged clusters featuring both MicroCeph-managed and unmanaged disks; regression tests ensuring detection logic fails closed; rollback tests verifying topology cache clearing restores the pre-phase state without residue.
- **Documentation:** Topology mapping guide explaining required operator inputs and the resulting CBT plan structure, a disk provisioning strategy document clarifying the MicroCeph vs CBT responsibilities, and a reminder that MicroCeph cluster bootstrap/join (including token issuance) remains an operator prerequisite outside Chopsticks automation.
- **Validation:** Run the topology command via the snap on a staging cluster, review the automatically selected CBT storage mode, confirm warnings surface for unsupported layouts, and sign off the decision record.
- **Rollback:** Clear cached topology data and revert to manual configuration selection if unexpected hardware layouts appear.
- **Known limitations:** Accurate detection depends on operator-supplied manifests for metadata (e.g., performance tiers) not exposed via MicroCeph tooling.

## Phase 4 – Configuration Assembly
- **Prerequisites:** Topology report approved and stored; dependency packaging plan (Phase 5) scheduled but not yet required.
- **Objectives:** Ingest operator-provided Ceph configuration fragments, render final `ceph.conf`, `ceph.keyring`, and CBT test plan templates that incorporate the discovered topology, while maintaining an intermediate staging area prior to finalization and intentionally stopping short of CBT execution.
- **Deliverables:** Configuration ingestion CLI, JSON Schema (or equivalent) describing acceptable fragment formats and merge semantics, schema validation rules, final rendering pipeline that triggers only after topology confirmation, and a configuration lint command that validates syntax/structure without invoking CBT. Provide example fragment library for common scenarios (RBD tuning, RGW workloads, debug logging) plus merge-conflict resolution guidance.
- **Tests:** Unit tests for parsing/validation (positive and negative cases); integration tests confirming rendered artifacts integrate topology data; lint command tests ensuring malformed inputs produce actionable errors; rollback tests verifying staged configuration removal restores baseline state.
- **Documentation:** Configuration handbook delineating ingestion vs. finalization phases, expected file locations, merge/override semantics, and rollback instructions; operator reference for providing correct fragments and interpreting lint output.
- **Validation:** Run the configuration lint workflow on a staging cluster using representative fragments, review generated artifacts for correctness, capture lint reports for traceability, and defer CBT dry-run execution to Phase 6 once bundled dependencies are available.
- **Rollback:** Withdraw staged configuration sets via a dedicated CLI, reverting to ingestion state without affecting prior phases.
- **Known limitations:** Relies on operator-supplied Ceph credentials; no automated retrieval from MicroCeph control plane; full CBT dry-runs occur in Phase 6 after dependency packaging completes.

## Phase 5 – Bundled Dependency Packaging
- **Prerequisites:** Configuration workflows pass validation; snap parts build cleanly; target nodes (controller plus participants) are prepared to install/refresh the Chopsticks snap.
- **Objectives:** Package all runtime dependencies (`pdsh`, `fio`, monitoring helpers such as `collectl`, `perf`, `blktrace`, optional tooling under evaluation like `seekwatcher`, `valgrind`, `cosbench`, and required Python libraries) directly inside the snap; finalize CBT vendoring; articulate which monitoring tools ship vs. remain out-of-scope; define snap size budgets; and document licensing plus update procedures. Ensure Chopsticks snap installation on every node is the supported distribution model so bundled binaries are accessible remotely.
- **Deliverables:** Snapcraft part definitions for each bundled dependency; monitoring support matrix (bundled, optional, excluded) delivered as YAML for reuse in documentation and runtime checks; aggregated third-party license manifest with automated extraction tooling (e.g., scancode); provenance verification (checksums/signatures) workflow; tooling to refresh vendored payloads while preserving `uv` lock reproducibility; snap size budget report with per-component estimates and CI guardrails; remote installation/refresh playbook for deploying the snap to follower nodes; and enhanced `uv` conflict detection scripts covering sequential environment activation, shared subprocess execution, and reconciliation guidance.
- **Tests:** Packaging regression tests confirming binaries are present and executable inside classic confinement; remote execution tests that install the snap on representative remote nodes and validate each bundled binary runs over SSH; license compliance checks driven by the automated scanner; size-budget test failing builds that exceed thresholds (e.g., ≤500 MB compressed); `uv` conflict detection tests ensuring Chopsticks core and CBT environments remain isolated yet compatible; rollback tests verifying dependency manifest reversion restores prior behavior.
- **Documentation:** Dependency inventory (versions, upstream URLs, update cadence), space budget policy and current totals, monitoring support matrix explanation (including rationale for excluded tools and hooks for future inclusion), remote installation instructions (controller and cluster nodes), bundled-tool refresh procedures, and licensing review workflow with blocking criteria.
- **Validation:** Build the snap and verify all bundled tools execute successfully on the controller and remote nodes using the supported snap installation model; capture size metrics and confirm they meet established thresholds; archive monitoring matrix, license manifest, and size report alongside the validation log.
- **Rollback:** Revert to the last known-good dependency manifest and lockfiles if regressions or space overruns occur; uninstall updated snaps on remote nodes and reinstall previous builds if validation fails.
- **Known limitations:** Bundling increases snap size and requires recurring license reviews; optional tooling not yet bundled is documented as such; each participating node must install the Chopsticks snap to access the packaged toolchain.

## Phase 6 – Execution Pipeline & Cleanup
- **Prerequisites:** Bundled dependencies validated and available within the snap; Chopsticks snap installed on controller (acting as CBT head) and all target nodes; operator accepts resource sizing guidance from Phase 1 architecture notes.
- **Objectives:** Implement commands to generate CBT runs, execute them via the packaged CBT (subprocess invocation from the `cbt-vendor` part) on the controller/head node, collect archives, enforce structured error handling (timeouts, partial failures, retry policies) aligned with Phase 1 standards, manage the optional `chopd.service`/timer, maintain the compatibility matrix with tested combinations, and deliver cleanup routines plus archive retention controls for CBT-generated resources (test pools, temp files, on-disk archives).
- **Deliverables:** Execution orchestrator module; systemd unit/timer definitions; retry/backoff and cancellation policies; cleanup CLI toggles (automatic vs manual) with retention settings (default keep latest 10 archives, operator-configurable); compatibility matrix update tooling integrating test outcomes; archive schema definition (directory layout, metadata catalog); retention scheduler (CLI/systemd timer) and disk space warning hooks.
- **Tests:** Integration tests executing representative CBT scenarios in controlled environments; fault-injection tests covering process crashes, timeouts, and interruption recovery; systemd unit tests verifying restart policies; cleanup validation ensuring MicroCeph cluster state returns to baseline; archive format regression tests comparing expected structures; retention/cleanup tests verifying default policies and operator overrides; rollback tests confirming disabling services and cleanup toggles restore baseline behavior.
- **Documentation:** End-to-end operator guide including invocation examples, error code reference, archive structure diagrams, cleanup policy descriptions, retention defaults and override instructions, architecture guidance reiterating controller=head model with SSH topology, and instructions for enabling/disabling the systemd units and timers.
- **Validation:** Run full CBT rehearsals on staging clusters using the snap, confirm archives match the published schema, verify cleanup removes CBT artifacts without disturbing MicroCeph workloads, assert retention policies behave as documented, and log results in the compatibility matrix (with runtime warnings for untested combinations).
- **Rollback:** Disable systemd units and revert to manual execution if regressions emerge; restore archived cluster snapshots if cleanup malfunctions; reset retention policies to defaults when overrides misbehave.
- **Known limitations:** Long-running benchmarks demand adequate host resources and may extend beyond default systemd timeouts; operators must size clusters accordingly and monitor disk usage for archives beyond the configured retention window.

## Phase 7 – Reporting & Observability Enhancements
- **Prerequisites:** Execution pipeline operational with stable archive format; monitoring support matrix from Phase 5 published and accessible.
- **Objectives:** Provide post-run analytics (plots, summaries); embed supported monitoring profiles (e.g., `collectl`, `perf`, `blktrace`) that were bundled in Phase 5; surface matrix-driven warnings when operators enable profiles needing excluded tooling; improve logging; and add optional artifact push targets plus scheduled health/log rotation timers.
- **Deliverables:** Reporting modules, monitoring configuration templates bound to the Phase 5 matrix, observability configuration CLI, storage backend adapters (e.g., object storage upload), runtime check that inspects the matrix before enabling profiles, and documentation snippets auto-generated from the machine-readable matrix.
- **Tests:** Unit tests for analytics transformers; snapshot tests comparing generated plots/summaries; observability integration tests ensuring timers and log rotations execute predictably; verification that monitoring profiles activate only when dependencies were bundled and emit clear guidance when excluded tools are requested; rollback tests ensuring disabling observability features restores baseline logging.
- **Documentation:** Reporting feature reference, machine-readable monitoring support matrix (bundled/default/optional/unsupported) with per-tool prerequisites and overhead notes, operational guidance for enabling scheduled tasks, and instructions for interpreting matrix-driven warnings.
- **Validation:** Demonstrate analytics on captured archives, confirm monitoring data appears in reports, run timers, validate runtime matrix checks in success and failure scenarios, and document outcomes.
- **Rollback:** Disable observability features via configuration flags; remove timers if they cause contention.
- **Known limitations:** Advanced analytics may require optional dependencies that increase build size; external storage targets demand operator credentials; unsupported monitoring tools remain documented but inactive.

## Phase 8 – Release Hardening
- **Prerequisites:** All prior phases completed and validated.
- **Objectives:** Polish CLI UX, finalize documentation, perform snap upgrade simulations, conduct security and licensing reviews, and produce a release candidate.
- **Deliverables:** Release readiness checklist, installation/upgrade instructions, support and maintenance policy, signed release candidate snap, publication automation scripts, and a strict-confinement evaluation report outlining feasibility, required interfaces, blockers, and go/no-go criteria.
- **Tests:** Packaging tests using `snap try`/`snap install --dangerous`; automated upgrade simulations; regression test sweep across supported MicroCeph versions; verification that security review findings are addressed.
- **Documentation:** Final user guide, troubleshooting appendix, security review report referencing the threat model established in Phase 1, and an appendix describing strict confinement evaluation outcomes.
- **Validation:** Execute acceptance test suite on target operating environments, sign off on licensing/security artifacts, publish the release candidate for broader testing, and archive the strict confinement decision record.
- **Rollback:** Hold release and address blocking findings before reattempting publication; keep prior stable release available as fallback.
- **Known limitations:** None beyond issues surfaced during acceptance; strict confinement migration is deferred to Phase 9 if deemed feasible.

## Phase 9 – Strict Confinement Feasibility (Future Work)
- **Prerequisites:** Phase 8 releases a stable classic-confinement snap and strict feasibility is greenlit.
- **Objectives:** Prototype strict confinement profile, enumerate required interfaces, evaluate functionality gaps, and devise mitigation strategies (e.g., portals, service daemons) to replace classic-only capabilities.
- **Deliverables:** Prototype `snapcraft.yaml` strict profile, interface mapping document, gap analysis with mitigation proposals, and a migration playbook outlining phased rollout.
- **Tests:** Confinement validation tests ensuring key workflows function under strict interfaces; regression tests on SSH orchestration, CBT execution, and bundled tooling access; security tests confirming reduced attack surface.
- **Documentation:** Migration guide, risk register for strict confinement adoption, and update plan for operators.
- **Validation:** Present findings to stakeholders for go/no-go decision on strict migration; if approved, schedule dedicated implementation phase.
- **Rollback:** Retain classic confinement snap as fallback until strict build attains parity.
- **Known limitations:** Research phase only; additional implementation effort required post-approval.
